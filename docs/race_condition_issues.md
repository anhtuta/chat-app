# Race condition issues

Index of concurrency write-ups. Detail, examples, and Redis notes live in each numbered doc. Severity: [issue_severity_levels.md](./issue_severity_levels.md).

## Database / cross-request races

These happen across HTTP requests (and app instances). The shared state is Postgres (and for doc 31, MinIO/S3). JVM monitors cannot close them.

| Doc                                                   | Issue                                                                                       | Pattern                                                                     | Fix                                                                                                            | Why this fix                                                                                                                                                                                                                                                                      |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [19](./19_MESSAGE_MODERATION_OPTIMISTIC_LOCKING.md)   | Concurrent edit/delete on the **same** `messages` row (two edits, edit+delete, two deletes) | Lost update / same-row RMW (load → mutate → `save` with no version)         | Optimistic lock: `@Version` on `messages`; loser → HTTP 409                                                    | Contention is one row, not a family of APIs. Holding `FOR UPDATE` for the whole edit TX is heavier than failing the loser. `@Version` does **not** cover membership (doc 23). Redis is unnecessary for a single-row write.                                                        |
| [21](./21_LAST_MEMBER_LEAVE_CONCURRENT_JOIN.md)       | Last-member leave/archive vs join/add                                                       | TOCTOU on `archivedAt` + member count, then insert vs archive               | Pessimistic lock: `SELECT … FOR UPDATE` on `groups` (`lockActiveGroup`)                                        | Leave, add, and join must share **one** mutex. A CAS on `archived_at` alone does not serialize the participant insert. Same group lock as doc 24.                                                                                                                                 |
| [23](./23_MESSAGE_MODERATION_MEMBERSHIP_AUTH_RACE.md) | Group message edit/delete vs kick/ban/demote/leave                                          | Cross-table auth TOCTOU (`group_participants` check, then `messages` write) | Pessimistic lock: `FOR UPDATE` on the **actor’s** `group_participants` row                                     | The auth row is the mutex. Kick’s `DELETE`/`UPDATE` waits on that row, so you do not need to lock the whole group (that would serialize unrelated edits). Redis only works if kick/ban/leave take the **same** key — they do not today.                                           |
| [24](./24_MEMBERSHIP_MUTATION_AUTH_LOCK_ORDER.md)     | Membership APIs: auth/validate **then** lock (add, kick, ban, role, join-link, …)           | TOCTOU: permission or join-link state goes stale before the write           | Pessimistic lock: `lockActiveGroup` **before** auth; re-read role/link under the lock                          | All membership/role mutations of one group need a **shared** mutex. The `groups` row is that mutex (it does not magically lock `group_participants`). Redis could replace it only if **every** path uses the same key, with lease renewal + fencing + unlock **after** DB commit. |
| [31](./31_MEDIA_MULTIPART_UPLOAD_ID_INIT_RACE.md)     | Concurrent first `/parts`: two MinIO multipart upload ids, last writer wins in DB           | TOCTOU / RMW on `multipart_upload_id`, plus an irreversible provider create | CAS: `UPDATE … SET multipart_upload_id = ? WHERE id = ? AND multipart_upload_id IS NULL`; loser abort + reload | One-shot NULL → value claim. `FOR UPDATE` would hold a DB lock across MinIO RTT. `@Version` would force a retry loop. Redis is extra infra for one column.                                                                                                                        |

Docs 21 and 24 share `lockActiveGroup`. Doc 23 uses a **finer** lock on the actor’s participant row so Alice’s edit does not wait on Charlie’s.

## In-process (same JVM) concurrency

These protect **heap** on one instance: listener maps, debounce buffers, subscription counts. They are not substitutes for the table above. There is **no** `ReentrantLock` in this repo.

| Doc / code                                                                                                                                                 | Issue                                                                    | Pattern                                                     | Fix                                                                       | Why this fix                                                                                                                                             |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------- | ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [22](./22_DYNAMIC_RABBITMQ_LISTENER_REGISTRY_CONCURRENCY.md)                                                                                               | Two `startListening` on the same queue (or start vs stop)                | In-memory map TOCTOU (`HashMap` containsKey → create → put) | `ConcurrentHashMap.computeIfAbsent` / atomic `remove` then stop           | Registry lives in this JVM only. Per-key atomic register avoids a class-wide `synchronized`. `container.start()` stays short while the bin lock is held. |
| [GroupSummaryUpdatePublisher](../chat-app-backend/src/main/java/com/hello/chatapp/service/GroupSummaryUpdatePublisher.java) (see [spring.md](./spring.md)) | Concurrent sidebar updates for the same `groupId` (buffer + flush timer) | Shared in-memory debounce state                             | `ConcurrentHashMap` of per-group objects + `synchronized (pendingUpdate)` | Different groups must run in parallel; only one group’s buffer needs a monitor. A process-wide lock would stall unrelated groups. Not a DB race.         |
| [CustomRabbitMQBrokerHandler](../chat-app-backend/src/main/java/com/hello/chatapp/config/CustomRabbitMQBrokerHandler.java)                                 | Concurrent subscribe/unsubscribe vs binding counts                       | Shared in-memory maps                                       | `ConcurrentHashMap` + `synchronized` on the binding-sync method           | Instance-local STOMP → Rabbit binding counts. Must be thread-safe on this node; other nodes have their own maps.                                         |

`media-processing` also uses `ConcurrentHashMap.newKeySet()` for in-memory job-id dedup (`InMemoryMediaProcessingJobDeduplicationStore`). That is process-local, not a cross-instance lock.

## Why not `synchronized` / `ReentrantLock` / `ConcurrentHashMap` for docs 19–24 / 31?

Those APIs only order threads **inside one JVM**. Chat requests hit **multiple instances** (or at least multiple threads that all talk to **Postgres**). A lock in instance A’s heap does not stop instance B from kicking Alice or joining an archived group.

| Tool                             | What it can protect                                                                                | Why it is the wrong mutex for 19 / 21 / 23 / 24 / 31                                                                                   |
| -------------------------------- | -------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `synchronized` / `ReentrantLock` | A monitor in this process                                                                          | Other pods never wait; lock dies on restart; not tied to a DB transaction                                                              |
| `ConcurrentHashMap`              | Thread-safe in-memory maps / atomic per-key compute                                                | Membership, messages, and upload ids are not map entries in this heap                                                                  |
| Redis lock                       | Cross-instance mutex **if** every path uses the same key (renewal + fencing + unlock after commit) | Discussed in docs 23/24; **not implemented**. Still weaker than a row lock that already coordinates with `DELETE`/`UPDATE` of that row |
| DB row lock / `@Version` / CAS   | The actual shared rows                                                                             | Survives multiple instances; lock/version ends with the transaction (or fails the loser)                                               |

Use JVM locks when the invariant is “this process’s map/buffer/listener.” Use DB (or a carefully designed Redis mutex) when the invariant is “this row in Postgres.”
